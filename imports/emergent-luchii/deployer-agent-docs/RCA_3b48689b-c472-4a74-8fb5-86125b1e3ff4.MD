## (1) Exact production exception behind "chat stream error (attempt …)"

It is **NOT** the historical budget/429. Every chat reply now fails with an **auth error — the LLM key is rejected as inactive**:

```
2026-09-18 00:45:37 - server - ERROR - chat stream error (attempt 2)
emergentintegrations.llm.chat.ChatError: Failed to start streaming completion:
  litellm.AuthenticationError: AuthenticationError: OpenAIException - API key is inactive
litellm.llms.openai.common_utils.OpenAIError: API key is inactive
openai.AuthenticationError: API key is inactive
  at litellm/llms/openai/openai.py async_streaming -> make_openai_chat_completion_request
```

Both retry attempts hit the same `AuthenticationError`, so `_luchii_stream` emits the honest "⚠ Luchii hit turbulence…" fallback. The **same failure cascades to the chat-memory feature**: `server - ERROR - memory extraction failed` at `server.py:183 _extract_memory` at identical timestamps (00:44–00:45) — same LLM call, same inactive key.

Contrast with the earlier incident (litellm 429 `budget_exceeded`, $36.47 > $35.95). That was resolved by recharge. **This is a different, distinct failure: `API key is inactive` (401-class auth), not a 429 budget cap.**

## (2) Production EMERGENT_LLM_KEY vs the funded preview key — STALE / DIFFERENT

- `EMERGENT_LLM_KEY` **is present and non-empty** in the production secret store (`is_empty:false`).
- Values are KMS-sealed and never returned, but upstream's own verdict on the stored value is decisive: **"API key is inactive."** Preview uses the current funded key and works right now; production's stored value is rejected as inactive.
- **Root cause:** the production secret holds a **stale/rotated key value** that differs from the current funded key in preview. When the user recharged/rotated the key in preview, production kept the old value — **pre-existing deployment secret values are NOT overwritten on redeploy**, so every subsequent redeploy carried the deactivated key forward.

## (3) Voice (/api/voice/speak, Coqui XTTS) — memory-starved at tier_0

- Production log at container start: `server - WARNING - Deferring ML preload — only 0.3 GB memory available (memory vault + voice engines will lazy-load on demand)`.
- tier_0 memory **limit is 512Mi (~0.3 GB usable after overhead)** — far below what XTTS needs. The model can't preload and an on-demand lazy-load will fail under the cap, so `/api/voice/speak` returns **503 'voice engine warming up'**, exactly as reported.
- Note: there is **no OOMKilled event and restart_count is 0** on both pods — the container isn't being killed; the model simply can't load within 512Mi. (GET probe of /api/voice/speak returns 405 Method Not Allowed → endpoint exists, POST-only.)

## (4) Mid-rollout? NO — production is running the correct, fully-promoted image

- Run history shows the most recent run (3b48689b) is `success` and is the active/live run; there is **no in-flight or failed run**.
- Both replicas run the active image `…/ai-gateway-demo:3b48689b…`: pod `lfd79` up since 2026-09-17 06:55, pod `xm4g7` up since 2026-09-18 00:32. The newer pod is a **replica reschedule onto an autoscaled node (same image/run)**, not a half-updated deploy. Startup-probe 503s on xm4g7 were transient (backend warming during boot); it is now `ready`.
- So production is **not** serving a half-updated image. The chat/voice failures are runtime config/resource issues, not a bad rollout.

## Remediation (owner actions — none are a code fix)
1. **Chat + memory extraction (primary):** Update the **EMERGENT_LLM_KEY value in Deployment Panel → Secrets tab** to the current funded key (the one working in preview), Save, then redeploy. A plain redeploy alone will NOT fix it — pre-existing secret values are not overwritten; the value must be edited in the UI.
2. **Voice/XTTS:** Upgrade the deployment tier in **Deployment Panel → Resources** to a higher-memory tier so XTTS fits in memory (512Mi is insufficient). After the key fix, voice will still 503 until memory is raised.
3. No manifest/source change required; no rollback needed (active image is correct).
